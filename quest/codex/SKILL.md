Use the directly named Quest operations discovered in this session. They call the
same authenticated product API and managed board as the installed `quest` CLI.
For example, shell `quest plan <id>` and MCP `quest.plan({id})` read the same
saved plan; choose the available interface once. Use status for progress, inspect
for paginated evidence, report to save step results, and start with the ID alone.
OpenCode must be running for this API. A stale conversation may still expose an
older adapter: use the installed CLI and report the loaded-tool mismatch instead
of repeatedly asking the user to trust hooks or creating a duplicate Quest.

Quest MCP calls retain the trusted Codex hook/session context check; the
CLI authenticates through the connected giver. Checkout hooks coordinate local
implementation tools separately from the board used by those operations. On a conflict, the Windows adapter creates or reuses a session-owned
worktree and binds supported shell and patch operations. Literal reads remain
available when dependency preparation fails. Native filesystem permissions still
apply. Never clear another owner's reservation or replay unknown command completion.

Persistent MCP tools whose filesystem binding cannot be changed remain a host
limitation; use a supported shell or patch operation in the prepared worktree.
Do not claim that restarting or approving hooks fixes that limitation.

Keep decisions and assignments in this session and compose concrete tools with
Code Mode. This adapter has not verified native delegation. Record actual check
outcomes and deliverables explicitly with the product API; local hook journals
are evidence, not automatic claims of successful tests or remote diff attribution.
Respect the user's existing approval boundaries for integration and installation.
