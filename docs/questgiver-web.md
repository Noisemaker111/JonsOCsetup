# QuestGiver web

A site you open from any browser, sign into with Google, and use instead of the terminal: the Quest
Giver conversation streaming live, the Quest board, usage. The OpenCode 2 host and the Quest Giver
keep running on your computer or VPS; the site reaches them through a link the machine opens
outward. Other people use the same site with their own machines.

Source lives in `questgiver/` in this repository: `protocol/`, `relay/`, `connector/`, `site/`.

## What using it is like

- Open the site. Sign in with Google once per browser; the sign-in renews itself every visit and ends
  only when you sign out or revoke it. No keys, tokens or session strings are ever typed or pasted.
- First time on a machine: run `questgiver link` there once. It opens the browser on a page that says
  "Link this computer to <your Google account>?" with the machine's name. One click. A machine
  without a browser prints a short code to type at `/link` instead.
- After that the machine reconnects by itself on boot and after network loss. Nothing on the machine
  expires, because it proves itself with a key it generated, not with a secret someone issued.
- The site lists your machines with online/offline. Pick one and you are in the giver conversation.
- Machines page: rename, see last seen, unlink. Unlinking cuts the live connection immediately.

## Pieces

- **Site** (`questgiver/site`): React, Vite, TypeScript. Served as static assets by the relay Worker,
  so there is one origin and cookies need no cross-site handling.
- **Relay** (`questgiver/relay`): one Cloudflare Worker.
  - D1 holds users, browser sessions, machines and pending link requests.
  - One Durable Object per machine holds that machine's connector WebSocket (hibernating, so an idle
    machine costs nothing) and carries browser requests across it.
  - The Worker authenticates every browser request from the session cookie, checks the machine
    belongs to that user, then forwards to the machine's Durable Object.
- **Connector** (`questgiver/connector`): a Bun process on the machine, started with the host.
  - Dials `wss://<site>/connect` outward. No inbound port, no router or firewall change, no tunnel
    product.
  - Forwards to three local targets and attaches the local credential for each, so none of them
    ever leaves the machine:
    - `host`: the OpenCode 2 server (`/api/*`, Basic auth from the host's service registration).
    - `quest`: the Quest API (bearer token from the registry receipt, found the way `quest` finds it).
    - `usage`: `usage/account-api.ts` called in-process.
  - Forwards only what its allow-list names. HTTP and event streams are carried; WebSocket upgrades
    are not, so the host's PTY endpoints are unreachable from the web.
- **Protocol** (`questgiver/protocol`): the frame types both ends of the link share.

## The link, in detail

- The browser makes ordinary HTTP calls to `/m/<machine>/<target>/<path>`. The relay turns each into
  frames on the connector's WebSocket and turns the answer back into an HTTP response, streaming
  when the answer streams. The host's `/api/event` and the Quest API's event stream arrive in the
  browser as normal `EventSource` streams.
- Because host calls pass through byte-for-byte, the site uses the host's own generated client
  against `/m/<machine>/host`, and a host update changes nothing in the relay.
- Frames: `open` (request line, headers), `body` (chunk), `end`, `abort`, each tagged with a stream
  number; the same four back. A browser disconnect sends `abort` so the machine stops streaming.
- Machine offline: requests answer 503 with a body the site shows as "this computer is offline",
  and the site retries when the machine's presence flips.

## Identity

- Google sign-in is OpenID Connect authorization-code with PKCE, handled in the Worker. The only
  thing kept from Google is the subject id, email, name and picture.
- The browser session is a random id in an `HttpOnly; Secure; SameSite=Lax` cookie; D1 stores only
  its hash. Every request slides its expiry forward.
- State-changing requests must carry the site's own `Origin`; anything else is refused.
- A machine identity is an Ed25519 key pair generated by the connector and kept in the machine's
  state directory. Linking stores the public key against the user. Each connection signs a nonce the
  relay issues; the relay stores nothing that could impersonate the machine.
- Link requests are single-use, short-lived, claimable only by a signed-in user, and show the
  machine's name and key fingerprint on both screens so a wrong code is visible before the click.

## Changes on the machine side (this repository)

- **The giver runs without a terminal.** `scripts/opencode-runtime.mjs:75` starts the host as
  `opencode2 --standalone`, so the host and the giver die with the TUI window. The managed runtime
  gets a headless start that runs the host server for the same channel config and state, the
  connector beside it, at sign-in to Windows (or as a systemd unit on a VPS). `oc` then attaches to
  that server with `--server` and becomes one more client of the same giver. How the giver's
  location is woken without a TUI is to be traced, not assumed.
- **The Quest API gets a change stream.** `GET /events` (same credential, same no-`Origin` rule),
  one line per saved change carrying the Quest id. Every change, from any process, appends to
  `journals/<questID>.jsonl`, so the stream watches that directory. The board updates live from it.
- **Nothing about the Quest API's local rules changes.** It stays on 127.0.0.1, keeps refusing
  browser-origin requests and keeps its per-boot token. The connector is a local client like `quest`.

## Site screens

- Conversation: the giver session, streaming parts, tool calls, permission and form requests
  answered in place, prompt box with steer/queue, interrupt.
- Board: the four groups of `list({view:"report"})` in its order and words, live.
- Quest: description, steps with state, runs, artifacts; create, edit, start, archive, reopen.
- Usage: accounts, pools, pacing, resets.
- Machines and account.
- Works on a phone.

## Risks that stay open

- The relay terminates TLS, so whoever operates it can read traffic of every linked machine. Fine
  while the users are Jon; before strangers rely on it, the browser and connector should encrypt
  to each other with keys exchanged at link time, leaving the relay blind.
- A signed-in browser can make the agent run anything on the machine. The Google account is the
  whole perimeter, so account-level protections (2FA) are the machine's protection.
- The OpenCode 2 host is a preview; its API can move. Pass-through keeps the relay immune, the site
  is not.
